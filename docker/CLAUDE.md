# Docker packaging

Guidance for `docker/`. The root `CLAUDE.md` keeps only the constraints that bite from *outside* this directory; everything else about the image lives here.

## Preparing the contents

`./docker/prepare-for-building-the-image.sh` **must be run from the repository root** and is destructive to the working tree: it checks the GUI version (*five refusals, see the version string section of the root `CLAUDE.md` and `.claude/notes/version-string.md`*), compiles, then `git stash`es uncommitted changes — that order matters, since it is what makes the archive carry the working tree's version — renames `js/settings.js` to `js/settings.js.default`, `sed`s every `index.html`/`*.js` reference of `./js/settings.js` to `./js/settings/settings.js` (a workaround for Docker being unable to bind-mount a single file), tars `css/ images/ js/ favicon.png index.html` into `docker/contents.tar`, then `rm -r ./js/*`, `git checkout -- .` and pops the stash. It needs `tsc` and GNU `sed` (`gsed` on macOS). `docker/contents.tar` is a gitignored build artifact.

The `tar` call runs from `docker/` and takes **`-C ..` with bare item names** (`css images js favicon.png index.html`), not `../css/ ../images/ …`, and that is not a style preference: whether a `../` prefix survives into the archived member names depends on the archiver. GNU tar strips it while creating the archive (printing `Removing leading '../' from member names`), macOS's libarchive `tar` keeps it — so the same script produced different archives on Linux and on the machine this project is actually released from. An archive whose members are `../css/…` is one that **GNU tar then refuses to unpack at all**: `Member name contains '..'`, nothing extracted, and `$?` is 0, so it looks like an empty archive rather than a refusal (`tar -xPf` bypasses the check if an old artifact has to be opened). Docker's `ADD` sanitizes the paths itself and has always coped, which is why this went unnoticed — it costs nothing in the image and everything in being able to inspect or test `contents.tar` locally. Verified after the change: 0 members containing `..`, plain `tar -xf` extracts it, and `entrypoint.sh` run against the result serves the GUI and its rewritten `./js/settings/settings.js` reference. Any `contents.tar` built before this is still `../`-prefixed until it is regenerated.

The same call also passes **`--no-xattrs`**, because bsdtar archives extended attributes and GNU tar does not: the committed macOS-built artifact carries 87 xattr headers *per spelling* (libarchive writes both `SCHILY.xattr.…` and `LIBARCHIVE.xattr.…` for compatibility) — `com.apple.quarantine`, `com.apple.provenance`, `com.apple.macl`, `com.apple.metadata:kMDItemWhereFroms`, `com.apple.lastuseddate#PS` — which ride into the image layer and make GNU tar warn once per attribute (`Ignoring unknown extended header keyword`) on every read. `COPYFILE_DISABLE=1` does *not* cover them; that variable is about the AppleDouble `._` sidecar files, a different mechanism. The flag needs no OS branch: GNU tar stores no xattrs in the first place but accepts it regardless, verified here by building the archive both ways and getting **byte-identical** output (143360 bytes). What *would* need a branch is bsdtar's `--no-mac-metadata`, which GNU tar rejects outright — and it is not needed, since these archives contain no `LIBARCHIVE.mac-metadata` headers at all, only xattr ones.

Both of those scripts also had their shebang typo'd as `#/bin/…` without the `!`, which the kernel does not recognise, so they only ran because the invoking shell fell back to interpreting them itself — `prepare-for-building-the-image.sh` relies on `[[ ]]` and `==`, so under a `dash` fallback it would have broken. Both now say `#!`.

## `entrypoint.sh` and `src/settings.ts`

`docker/entrypoint.sh` generates `js/settings/settings.js` from the `.default` on first start by `sed`ing in `RCLONE_ALLOW_ORIGIN_{SCHEME,HOST,PORT}` / `RCLONE_USER` / `RCLONE_PASS` — those `sed` patterns match the literal default lines in `src/settings.ts` (`host: "http://127.0.0.1:5572",`, `user: null,`, `pass: null,`, `someExampleRemote`, …). **Changing those literals silently breaks the Docker image.**

## The `Dockerfile`

It takes the architecture from BuildKit's **`TARGETARCH`** (`amd64`, `arm64`, `386` map straight onto rclone's release names; `arm/v6`/`arm/v7` would additionally need `TARGETVARIANT`, which is why it is there commented out), so it is **BuildKit-only** — that plus `COPY --chmod` means `DOCKER_BUILDKIT=0` fails outright rather than falling back. A plain `docker build` still produces one architecture, the host's; a genuinely multi-arch image needs `docker buildx build --platform linux/amd64,linux/arm64 --push`. Build args/vars, the `buildx` invocation and Synology Container Manager setup are documented in `docker/README.md`.

The rclone download is checksummed against the release's `SHA256SUMS`, which is fetched over the same channel as the archive and so proves integrity, not authenticity (upstream PGP-clearsigns that file inline — there is no separate `.asc` — so real provenance would take `gnupg` plus a pinned fingerprint in the image). The matching line is written to a file rather than piped into `sha256sum -c -`, because a pipeline reports only the last command's status and BusyBox's `sha256sum -c` accepts empty input where GNU coreutils errors, so a `grep` that matched nothing used to pass silently. The `.zip` in that pattern is load-bearing too: the same version and architecture are also listed there as `.deb` and `.rpm`.

### The `LABEL` layer

It carries the standard [OCI annotations](https://github.com/opencontainers/image-spec/blob/main/annotations.md). Four things about it are deliberate.

It sits **last**, because `VCS_REF` changes with every commit and a label declared earlier would bust the cache of everything below it (labels add no filesystem layer themselves, so there is no cost to keeping them at the bottom).

**`GUI_VERSION_VALUE` and `VCS_REF` have empty defaults** rather than real ones: the GUI version lives in `guiVersion` in `src/main.ts`, so a default spelled out in the `Dockerfile` would silently drift from it, and a commit hash cannot be derived inside a build at all — `docker/README.md` passes both as `--build-arg` next to the `RCLONE_VER`/`GUI_VER` the tags are already built from, and omitting them only leaves those two labels empty.

**`org.opencontainers.image.version` is the GUI version, not rclone's** — that is what the footer shows and what the release tags use — and the bundled rclone version gets a label of its own (`dev.decovar.rclone-rc-web-gui.rclone-version`) rather than being crammed into the standard field, since the image tags (`rclone_<rclone version>-gui_<gui version>`) are made of both.

And `licenses` is **`AGPL-3.0-or-later`**, which is the author's intended grant, decided explicitly and matching the `GPL-3.0-or-later` of the yt-dlp image this was modelled on. **Don't "correct" it to `AGPL-3.0-only`**, which is what a reader checking the premise against `LICENSE` alone will be tempted to do: that file is the bare AGPLv3 text and so reads as the narrower grant on its own, but the README's `## License` section spells out "either version 3 of the license or (at your option) any later version", and the label follows the README. Those two are the only places the licence is stated — there are no per-file headers, and nothing in `index.html`, `src/` or `docker/entrypoint.sh` mentions it — so they have to move together.

## Credentials

**The image ships no default credentials, and `entrypoint.sh` refuses to start without them.** That guard is not politeness, it is the whole point of removing the old hardcoded `rclone`/`enolcr`, and both failure modes were measured against a live `rcd`: quoted-but-empty (`--rc-user "" --rc-pass ""`) makes rclone serve **the entire rc API unauthenticated** — `POST /core/version` with no `Authorization` header answers 200 — while *unquoted* empty variables make the words vanish from the command line altogether, leaving `--rc-user --rc-pass`, where pflag eats `--rc-pass` as the user name. That second one is the nastier of the two: `rcd` starts and looks healthy, rejects an unauthenticated request with 401 as if all were well, and lets anyone in with the username `--rc-pass` and an empty password — a credential pair derivable from a public Dockerfile.

Hence both the `[ -z … ]` check and the quoting of **every** variable in that `rclone rcd` line (which also fixes a password containing a space, verified end to end). `entrypoint.sh` also runs under `set -eu`, so a failed `mv` of `settings.js.default` — what an unwritable bind-mounted `js/settings/` looks like — exits instead of serving a GUI whose `settings.js` 404s, and it ends in **`exec`** so rclone replaces the shell as PID 1 and gets the `SIGTERM` from `docker stop`.

## `/config` and the config file

`ENV RCLONE_CONFIG` sets rclone's `--config` explicitly to **`/config/rclone.conf`**, and the default config is **not baked into the image** — `entrypoint.sh` creates it on first start, exactly the way it creates `settings.js`. That is the whole point of the layout: `/config` is a mount point, and a bind mount *hides* whatever the image has at that path, so a baked-in config is only visible for as long as nobody mounts anything.

The previous arrangement kept it at `/home/rclone/.config/rclone/rclone.conf` and worked around the hiding by telling users to create a **named volume** (`docker volume create -o o=bind -o device=…`), which Docker seeds from the image content on first use — a lot of ceremony, out-of-band from `docker run`, and resting on copy-up behaviour a reader has to already know about. Generating the file instead means an ordinary `-v /host/config:/config` works, and "I have an existing `rclone.conf` and want a new container to use it" becomes "copy it into that folder first", since the seeding is skipped whenever the file already exists (deliberately once-only, so deleting or renaming the `disk` remote is not fought with on every restart).

Two consequences worth keeping straight. This **was a breaking change**, done knowingly: a container started with the old mount reads a config that only ever held the `disk` alias, so the user's remotes are silently absent, which is why `docker/README.md` opens "Running a container" with an upgrade note. And because bind-mounted folders keep their host ownership while the container runs as uid 1000, the seeding can fail on permissions — so it exits with a message naming the folder, the uid, and both fixes (`chown -R 1000:1000` on the host, or `--user`/`user:` to run as the owning uid). The `settings.js` `mv` carries the same hint for the identical failure.

**`--user` is only viable because `RCLONE_CONFIG` is explicit**: rclone never has to resolve `$HOME`, which an uid absent from the image's `/etc/passwd` would get as `/`. That does still catch SFTP keys, since rclone's own `~/.ssh` discovery *does* use `$HOME` — hence `.ssh` stays at `/home/rclone/.ssh` rather than moving under `/config`, and the README notes `-e HOME=/home/rclone` for the `--user` case.

PUID/PGID remapping (the linuxserver.io pattern) was considered for that ownership problem and rejected: it needs the container to start as **root**, adds `shadow` (BusyBox has no `usermod`) and `su-exec`, and `chown -R`s bind-mounted folders at every start — i.e. rewrites ownership of *host* files, on a NAS where that tree is shared with other containers. `--user` is the runtime's own answer to the same problem, from outside and unprivileged, so the image stays non-root end to end.

The image still `mkdir -p`s the config folder (and now `chown`s it) so an unmounted run or a fresh named volume works. **Keep that `mkdir`** even though nothing writes the config at build time any more: the previous version got away without it only because `RUN rclone --version` sat on the line above — commented "not needed really", while in fact rclone creates its config folder on startup as a side effect (verified with `env -i HOME=… rclone --version`), so that line was load-bearing and reordering the layers would have broken the build.

## Release packages

They come from `git archive`-style exports — `.gitattributes` marks `.github/`, `docker/`, dotfiles, `CLAUDE.md`, `/.claude/`, the Sublime project and `screenshot.png` as `export-ignore`.

## Image signing

Published images are signed with **cosign** and a plain key pair: `cosign.pub` in the repository root, `cosign.key` encrypted with a passphrase and listed in the root `.gitignore`. The release steps are in `docker/README.md` ("Signing the image"), the verification steps for users are in the same file ("Verifying the image"), and this section is the *why*.

**Docker Content Trust is not an option and is not worth investigating again**: `docker trust sign` runs against Notary v1, which is retired — brownouts of `notary.docker.io` started in July 2026 and it shuts down on **2026-12-08**, with the first phase back in August 2025 already breaking pulls for anyone with `DOCKER_CONTENT_TRUST=1`. The two live options are cosign (Sigstore) and Notation (Notary Project v2); Notation was rejected because a verifier needs a trust store and a trust policy JSON rather than one public key, which is more ceremony than this project's users should be asked for.

**A key pair rather than keyless**, because the release is a manual `docker buildx build --push` from the author's laptop and there is no CI (`.github/` holds only `FUNDING.yml`). Keyless would mean an interactive browser OIDC flow on every release and a verify command naming an email address plus an issuer in `--certificate-identity`/`--certificate-oidc-issuer`, where a key pair gives one stable public key that is published once. Keyless only becomes the better choice if the release ever moves into a GitHub Actions workflow, where the identity becomes the workflow itself and there is no secret to leak. The cost accepted in exchange: a bare key pair has **no revocation**, so a leak means generating a new pair and editing the README.

**`cosign.pub` is in the repository root and not in `docker/`**, because `.gitattributes` marks `/docker/` as `export-ignore` and a key placed there would be absent from the release archives — the one place a user who did not clone the repo would look for it. Don't add an `export-ignore` line for it either.

**Signatures are stored in the default legacy scheme — a `sha256-<digest>.sig` tag in the same repository — and the cleaner-looking OCI 1.1 referrers mode is deliberately not used.** Verified against cosign **v3.1.3** (the binary, not the docs): `--registry-referrers-mode` has an **empty** default, and `cmd/cosign/cli/sign/sign.go` only takes the `WriteSignaturesExperimentalOCI` path when it is explicitly set to `oci-1-1`, falling through to `WriteSignatures` (the tag scheme) otherwise. On the *verify* side the referrers lookup sits behind `--experimental-oci11`, which defaults to **false** and is deprecated with the message "OCI referrers will be the default behavior in future versions". So publishing in referrers mode would force **every verifier to pass an experimental flag**, and third-party tooling might not pass it at all — which costs more than the tag clutter it saves.

Two traps in re-deriving this: the v3.0.0 changelog lists "container signatures stored as an OCI Image 1.1 referring artifact" among the capabilities that are "on by default" in v3, which is **not** what v3.1.3 does, so don't take that sentence at face value; and Docker Hub is not the blocker, since it does serve the referrers API (verified: `/v2/decovar/rclone-rc-web-gui/referrers/<digest>` answers 200 with a valid empty index, and `bitnami/nginx` has a real `application/vnd.cncf.notary.signature` referrer indexed there). Revisit once the verify side stops being experimental. `COSIGN_REPOSITORY`, which parks signatures in a separate repository, was rejected for the same reason: the verifier would have to set it too.

**The index digest is signed and `--recursive` is deliberately omitted.** Pulling by tag resolves to the index digest and records it in `RepoDigests`, so both `cosign verify --key cosign.pub <repo>:<tag>` and a verification of what `docker` recorded hit the signature. `--recursive` (which walks the index children — `mutate.ErrSkipChildren` is what stops the walk when it is off) would additionally sign every child manifest: for a two-platform `buildx` push that is 2 image manifests plus 2 provenance attestation manifests, so **5 `.sig` tags per release instead of 1**, in a tag list that is otherwise nine hand-made tags. What it buys is per-platform digest verification, which is what a Kubernetes admission controller resolves to — so add it if this image ever has to satisfy such a policy, and not before. For a sense of the scale of that clutter: `bitnami/nginx` has **640 of its 642 tags** being `sha256-…` signature artifacts.

**Rekor is no longer optional**: `--use-signing-config` defaults to true, and with it `--tlog-upload=false` is refused outright (the error names `cosign signing-config create` as the way to build a signing config with no transparency log service). So every signature is publicly logged, which is wanted here anyway. **Verifiers need cosign v3 or newer**, because `--new-bundle-format` defaults to **true** on both `sign` and `verify` in v3.1.3 and is deprecated as "this will be the only supported format in future versions".

The digest comes from `buildx`'s `--metadata-file` (`containerimage.digest`), written to `/tmp` so that `docker/.gitignore` — which is just `*.tar` — needs nothing added. One signature covers every tag pointing at that digest, so pushing the versioned tag and `latest` in one `buildx` invocation is what makes a single `cosign sign` enough; two builds are two digests and two signatures.

**None of the signing itself is verified end to end**, and it cannot be from the dev container: there is no `docker` and no Hub credentials in here. What *was* checked, with a checksum-verified cosign v3.1.3 binary in the scratchpad: every flag name and default quoted above, that `--tlog-upload=false` really is refused, and `cosign verify --key cosign.pub decovar/rclone-rc-web-gui:latest` against the live registry — which parses the key, reaches Docker Hub anonymously and fails with `Error: no signatures found`, i.e. exactly the command the README hands users, minus the signature. Also worth knowing for whoever fetches that binary next: the release's `cosign_checksums.txt` lists the SBOM as `cosign-linux-arm64_3.1.3_linux_arm64.sbom.json`, so a `grep -F cosign-linux-arm64` matches two lines and the `sha256sum -c` then fails on a file that was never downloaded — the same trap as the `.zip` suffix in the Dockerfile's rclone checksum, and it wants the same anchoring.

Note what the signature does and does not say: it identifies who pushed the image, and it does nothing about the rclone download's authenticity gap documented above (that one is integrity-only, absent `gnupg` and a pinned fingerprint).
